# SEAM Protocol — v0.1.0

> **Structured Engineering Awareness Method**

SEAM is a minimalist protocol for human-AI collaborative software development.
It defines how engineers maintain structured control over systems they no longer write line-by-line.

> **Note:** SEAM v0.1.0 is a proposal — an early attempt to standardize a practice
> that many teams are inventing independently. It has not been rigorously tested across
> diverse codebases. Adopt it critically. Break it. Tell us what doesn't work.

---

## Artifacts

### `SEAM.md`
This file. The protocol definition. Versioned by the SEAM project.
**Never edited by users.** Included in any repo that adopts SEAM.
The agent reads this to understand the rules.

### `{project}.seam.md`
The living map. The user's artifact.
Generated by the agent from an existing codebase, then curated by the human.
Version-controlled alongside the code. This IS the product at the intention level.

### Pins
Single-line annotations in source code linking implementation back to nodes.

```javascript
// @seam: cart.total.contract
function calculateTotal(cart) { ... }
```

Place the pin on the primary entry point for the node. The agent writes pins when implementing from the map.
A file with no pins is invisible to SEAM — governed only by its contract boundary.

Pins are lightweight anchors — helpful but not load-bearing in v0.1. The `.seam.md` map is the source of truth. If pins drift, the map still works.

Pin syntax varies by language:
- `// @seam: node.id` — JavaScript, TypeScript, Java, C, Go, Rust
- `# @seam: node.id` — Python, Ruby, Shell
- `-- @seam: node.id` — SQL, Lua, Haskell
- `/* @seam: node.id */` — CSS, multi-line contexts

## The Node Schema

Every entry in `{project}.seam.md` is a **node**. Nodes describe load-bearing concerns —
not files, not functions, but *risks, contracts, and decisions* worth a human owning.

```markdown
## {domain}.{concern}

status: owned | draft | watch | gap
risk: high | medium | low
why: one sentence — the reason this node exists, often a past failure or key decision
contract: what must always be true about this behavior
symbols:
  - ClassName.methodName()
  - AnotherClass.field
file: path/to/the/primary/file
review: (optional) freeform — used for team communication about this node
```

### Field Rules

| Field | Required | Who writes it |
|-------|----------|---------------|
| `status` | yes | Human sets final status |
| `risk` | yes | Agent drafts, human confirms |
| `why` | yes | Human writes or approves |
| `contract` | yes | Human writes or approves |
| `symbols` | required for `owned` | Agent extracts, human verifies |
| `file` | recommended | Agent fills |
| `review` | optional | Human or agent — freeform team communication |

The `symbols` field is non-negotiable for `owned` nodes.
If you cannot name the symbols, you do not own the node yet.
This is intentional — symbol names are your emergency debugging index.

## Status Labels

Four labels. No more.

| Label | Meaning | Who sets it |
|-------|---------|------------|
| `draft` | AI-generated, not yet human-reviewed | Agent |
| `owned` | Human has read, approved, and can navigate this | Human only |
| `watch` | Known risk area, requires active monitoring | Human |
| `gap` | Load-bearing code exists here but is not yet mapped | Agent surfaces, human resolves |

### The `owned` Contract

When you mark a node `owned` you are asserting:
1. You have read the contract and it is accurate
2. You know the symbol names and could find them without a search
3. You understand the `why` — the history behind this decision
4. You could debug a production issue in this area without AI assistance

Do not promote to `owned` casually. It means something.

## Sync Rules (Agent Behavior)

The agent maintains bidirectional sync between the map and the codebase.
These rules define expected agent behavior — no dedicated tooling is required.
Any capable AI agent reading this file should follow these rules.

### Map → Code (Forward Sync)
When a node changes in `{project}.seam.md`:
- Agent updates the implementation to match the new contract
- Agent writes or updates `// @seam: {node.id}` pins in affected files
- Agent must not modify nodes marked `owned` without human instruction

### Code → Map (Reverse Sync)
When source code changes without a corresponding pin:
- Agent detects unanchored load-bearing code (DB writes, auth checks, money math, async failure paths, external calls)
- Agent creates a new `gap` node in the map
- Agent never silently ignores unanchored critical code

### Idempotency Rule
The agent may regenerate the map at any time safely:
- `owned` and `watch` nodes are **never overwritten**
- `draft` nodes are refreshed if underlying code changed significantly
- `gap` nodes are added for newly detected unanchored code
- Deleted code causes the corresponding node to be flagged for human removal

## What SEAM Covers

SEAM nodes should exist for:

- **Data mutations** — anything that writes to a database or modifies persistent state
- **Auth boundaries** — authentication checks, authorization rules, permission gates
- **Financial/inventory math** — any calculation where being wrong costs money
- **External integrations** — API calls, webhooks, third-party services
- **Async failure paths** — background jobs, queues, anything that can fail silently
- **Critical business rules** — the logic that makes your product what it is

SEAM nodes should NOT exist for:

- UI components with no business logic
- Utility functions with obvious behavior
- Configuration and constants
- Anything where being wrong is immediately visible and easily fixed

The goal is 5-15% of your codebase pinned. Not more. Discipline here is the whole point.

## Emergency Debugging Protocol

When production breaks:

1. Open `{project}.seam.md`
2. Find the domain where the failure is occurring
3. Read the contract — is this a contract violation?
4. Go directly to the symbols listed in the node
5. You are now in the right file, in the right method, without searching

This is why `symbols` is required for `owned` nodes.
In a crisis, you have seconds. The map gets you there.

## Versioning and Updates

**Canonical source:** https://github.com/lyoff/seam

SEAM.md is versioned. `{project}.seam.md` declares the protocol version it follows:

```markdown
# myapp.seam.md
seam-version: 0.1.0
```

### Staying current

Agents reading this file should periodically check the canonical source for newer versions. When a new version is available, the agent should notify the human — never auto-upgrade.

### Local overrides

Projects may customize SEAM behavior by adding an `overrides` block to the header of their `{project}.seam.md`:

```markdown
# myapp.seam.md
seam-version: 0.1.0
overrides:
  - pins: not used (codebase uses decorators instead)
  - risk: added "critical" level above "high" for PCI-scoped code
```

Overrides are project-local and take precedence over this spec for that project. The agent should respect them. Overrides do not propagate upstream — they are that team's adaptation.

If you find yourself overriding the same thing across multiple projects, [open an issue](https://github.com/lyoff/seam/issues). It probably belongs in the protocol.

## Open Questions

These are unsolved. SEAM v0.1 does not address them. If you hit them, [open an issue](https://github.com/lyoff/seam/issues).

- **Team ownership** — Can a node have multiple owners? What does ownership handoff look like?
- **Scale** — How do maps behave in monorepos, microservices, or systems with 100+ nodes?
- **Branch divergence** — How should `.seam.md` files merge across git branches with conflicting node changes?
- **Node lifecycle** — When should a node be retired vs deleted? What about deprecated code that's still running?
- **Cross-repo dependencies** — What about seams that span services? Does each repo own its side of the boundary?
